# 周边去哪儿：基于高德的地点推荐助手

## 1. 用途与适用场景

把「我在某地铁站，想找步行 15 分钟内的咖啡馆，最多 3 家，优先近一点」这类请求，转成可核对的地点推荐。适用于单轮、单起点、步行出行的周边探索。

不处理多站行程、跨城市经验迁移、长期记忆与设备定位：评测输入已提供明确的城市与起点坐标，直接取用即可。

## 2. 输入与需求解析

从用户输入中提取并逐项记下：

- 城市与起点坐标（由评测输入提供，不自行定位）。
- 地点类型或关键词（咖啡馆、餐厅、公园等）。
- 步行时间上限（如「15 分钟内」）。
- 推荐数量上限（如「最多 3 家」；未说明时按 3 家处理）。
- 偏好（如「优先近一点」）与其他硬性条件。

没有给出的条件不要自行补写。区分硬性条件与偏好：硬性条件用于过滤，偏好只用于排序。

## 3. 工具调用步骤

使用当前评测环境中高德 MCP Server 提供的能力。工具名以环境实际可用者为准（地点搜索常见命名如 `maps_around`、`maps_text_search`；步行路线常见命名如 `maps_direction_walking`），按工具自身的参数说明传参。

1. **地点搜索**：以起点坐标为圆心，按城市与地点类型或关键词发起搜索，取得候选地点的名称、地址、坐标与地点 ID。候选数量应多于最终推荐数量，以便筛选；可先取较宽范围，再按步行时间收紧。
2. **步行路线**：对每个候选，以同一个用户起点为 origin、候选地点为 destination 查询步行路线，取回步行距离（米）与预计耗时（分钟）。各候选彼此独立，不把上一候选当作下一站的起点。
3. **时间与距离只取自路线结果**：禁止用两点直线距离、坐标估算或常识推测代替步行耗时。路线查询未返回数值的候选，不列为符合条件的推荐。
4. **过滤**：删除超过步行时间上限、类型不符、缺少路线数据或地点 ID 重复的候选。
5. **排序**：有「优先近一点」等偏好时按路线耗时（或距离）升序；没有偏好时保持合理顺序，并在理由中说明依据。排序所用数值必须与表格中展示的数值一致。
6. **截取**：取前 N 个，N 为需求中的数量上限，最多 3 个。

## 4. 回答格式

先用一句话说明按什么条件检索，再给表格：

| 地点名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |

- 名称、地址来自地点搜索结果；距离、时间来自步行路线结果，沿用工具返回的数值与单位，不换算成与返回值不一致的写法。
- 推荐理由一句话，引用工具返回的客观信息（距离、耗时、类型）。不写营业状态、安静程度、排队情况、口味评价等无工具依据的判断。
- 表格后附一段简短说明，交代筛选与排序依据，例如「已排除步行超过 15 分钟的候选，按步行耗时升序排列」。

## 5. 异常与信息缺失

- **结果不足**：符合条件的地点少于 N 个时，只列出实际符合的，并说明「当前搜索范围内符合条件的地点不足 N 个」，可建议放宽步行时间或扩大范围。不用不符合条件的地点凑数，也不把超时地点标注为「仅供参考」后列入。
- **查询失败或服务异常**：如实说明地点搜索或路线查询未成功、失败发生在哪一步；不编造地点、地址、距离或路线。可建议稍后重试或放宽条件。
- **信息未核实**：用户问到营业状态、是否安静、排队、评分等，而工具未返回对应数据时，明确写「未核实」并说明缺少哪类数据，不做推测。
- **空结果**：明确说明没有符合条件的地点，不输出猜测的备选。

## 6. 提交前自检

- 每个推荐都有对应的地点搜索结果与步行路线结果。
- 步行时间来自路线查询，未用直线距离替代。
- 数量上限、时间上限等硬性条件全部满足，超时地点未列入。
- 排序与理由引用的数值一致。
- 结果不足、信息缺失、工具失败均有说明，无编造内容。
- 回答中未出现 API Key 或账号信息；运行环境与密钥由评测平台配置。
